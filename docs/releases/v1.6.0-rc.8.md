# GPS Time v1.6.0-rc.8

**Date:** 2026-11-04 · **Type:** pre-release (release candidate) · **Previous:** [v1.6.0-rc.7](v1.6.0-rc.7.md); last stable [v1.4.0](v1.4.0.md)

rc.7 with the aircraft stack fixed, in one PR (#178). On the owner's Pi on rc.7, `gps-time-readsb` exited 1 and restarted every few seconds, tar1090 wasn't installed, and dump978 and skyaware978 were disabled. Everything in rc.1 to rc.7 is still here. v1.5.0 stays skipped. **The formal soak waits for the antenna move.**

None of this changes chrony, gpsd or the PPS setup. All of it is inside the optional SDR stack (`GTP_SDR=1`), the web SDR (`GTP_WEBSDR=1`) and the feeders (`GTP_FEEDERS=1`).

## The cause (inferred, not observed)

The readsb unit reads its serial from `/etc/default/gps-time-sdr` (not `/etc/gps-time`). The likely state on the Pi is an empty `GTP_SDR_1090_SERIAL=` there. readsb then starts with `--device` and nothing after it, takes the next option as the device, and exits 1; `Restart=on-failure` loops. The installer skipped tar1090 for the same reason (no 1090 MHz serial), so `/tar1090/` had no page. The rc.8 installer checks this before changing anything, and its check after the install shows the actual state either way.

## What the upgrade changes on the station

With `GTP_SDR=1`:
- **The install stops at the preflight** if `GTP_SDR_1090_SERIAL` is empty (here and saved). Set it to the 1090 MHz dongle's serial (`00000001` now), or `none`.
- **`/etc/default/gps-time-sdr`** gets the serials you pass; a deliberate `none` is saved as `none`.
- **New files:** `/etc/udev/rules.d/61-gps-time-rtl-sdr.rules` (if the web SDR hadn't added it), `/usr/local/share/gps-time-tar1090/html` (tar1090, now that the serial is set), `/usr/local/share/gps-time-skyaware978/html` (dump978 is cloned once more for its page, at the same commit).
- **The units** `gps-time-readsb`, `gps-time-dump978` and `gps-time-rtl-tcp` get `ExecCondition=`; readsb and dump978 a start limit.

With `GTP_WEBSDR=1`:
- **`gps-time-websdr.service`** loses its fixed `Conflicts=`; **`gps-time-websdr.service.d/gps-time-dongle.conf`** names the units on its dongle; `/etc/default/gps-time-websdr` gets `GTP_WEBSDR_SHARES`. Deploy with `GTP_WEBSDR=1` whenever the SDR stack's serials change, so the drop-in follows them.

With `GTP_FEEDERS=1` and PiAware: its start-up helper also sets the UAT receiver (`other`, 127.0.0.1:30978, or `none`).

## Deploy

From a clean working tree on Windows, in a normal PowerShell window. These are the flags for the owner's Pi today: one dongle in use for 1090 MHz and the web SDR (SN 00000001), the 978 MHz dongle (SN 00000978) as the second one. Empty flags aren't passed, and the Pi keeps its saved settings.

```powershell
git fetch --tags
git checkout v1.6.0-rc.8
git describe --tags --dirty          # must print exactly v1.6.0-rc.8

$env:GTP_SDR = '1'
$env:GTP_SDR_1090_SERIAL = '00000001'    # required now; 'none' for no 1090 MHz role
$env:GTP_SDR_978_SERIAL = '00000978'     # '' keeps it off with one dongle; 'none' clears it
$env:GTP_SDR_PPS_SERIAL = ''             # no PPS-marker dongle
$env:GTP_TAR1090 = '1'                   # the 1090 MHz map
$env:GTP_WEBSDR = '1'                    # re-run so its dongle drop-in follows the serials
$env:GTP_WEBSDR_SERIAL = '00000001'      # the 1090 MHz dongle: readsb pauses while it runs
$env:GTP_WEBSDR_PORT = '8073'
$env:GTP_WEBSDR_MAX_HOURS = '4'
$env:GTP_WEBSDR_AUTH = '0'
$env:GTP_WEBSDR_REMEMBER_DAYS = '30'
$env:GTP_WEBSDR_HF = 'off'
$env:GTP_FEEDERS = '1'                   # each feeder stays off until turned on in Administration
$env:GTP_FEEDERS_PIAWARE = '0'
$env:GTP_FEEDERS_CUSTOM = ''
$env:GTP_INDEPENDENT_REFS = ''
$env:GTP_KEEP_DHCP_NTP = ''
$env:GTP_CLIPS_DIR = ''
$env:GTP_CLIPS_MAX_MB = ''
$env:GTP_SDR_NODE = ''
$env:GTP_NODE = ''
$env:GTP_NODE_STATION = ''
powershell -ExecutionPolicy Bypass -File .\scripts\deploy-to-pi.ps1 -PiHost $PiHost -PiUser $PiUser
git checkout main
```

- **Both dongles plugged in with the factory serial `00000001`** on one of them: the installer warns that rtl-sdr's device search could read it as device index 1. dump978-fa matches its serial exactly (SoapySDR `serial=`); how Debian's readsb matches `00000001` isn't verified. Giving the dongles the serials 1090 and 978 removes the doubt (`deploy/sdr-stack.md` → "Two dongles"). Then deploy with `GTP_SDR_1090_SERIAL='1090'`, `GTP_SDR_978_SERIAL='978'`, `GTP_WEBSDR_SERIAL='1090'`.
- **One dongle only:** set `GTP_SDR_978_SERIAL = 'none'`.

Then read the deploy output's `== SDR stack: check after 10 s ==` lines. Each decoder should say `is active` and its `aircraft.json` `exists`. Open Radio & SDR → Aircraft decoders, `http://<pi>/tar1090/` and `http://<pi>/skyaware978/`. Remove the flags afterwards (`Remove-Item env:GTP_*`).

## Not yet verified on a Pi

- The cause above: the check after the install will show whether readsb now runs. If it still fails with a serial set, its journal lines are printed.
- readsb (Debian's package) opening the dongle by serial `00000001` with both dongles plugged in.
- `ExecCondition=` and the start limit under the Pi's systemd.
- skyaware978's page against a live skyaware978, and PiAware reading dump978-fa's raw port.
- The web SDR on the 978 MHz dongle, and the handoff starting dump978-fa and skyaware978 again.
- Messages per second against readsb's own `stats.json`.
- Everything in [`v1.6.0-rc.7.md`](v1.6.0-rc.7.md) → "Not yet verified on a Pi" still applies.

## Rollback

Check out `v1.6.0-rc.7` and run the same deploy command (rc.7 accepts the same flags). It leaves the skyaware978 page, the udev rule and the web SDR's dongle drop-in. The drop-in conflicts with the same units rc.7's unit names when the web SDR is on the 1090 MHz dongle; otherwise remove it by hand:

```sh
sudo rm /etc/systemd/system/gps-time-websdr.service.d/gps-time-dongle.conf && sudo systemctl daemon-reload
sudo rm -r /usr/local/share/gps-time-skyaware978
```
