# GPS Time v1.6.0-rc.9

**Date:** 2026-11-04 · **Type:** pre-release (release candidate) · **Previous:** [v1.6.0-rc.8](v1.6.0-rc.8.md); last stable [v1.4.0](v1.4.0.md)

rc.8 with readsb fixed, in one PR. Everything in rc.1 to rc.8 is still here. v1.5.0 stays skipped. **The formal soak waits for the antenna move.**

None of this changes chrony, gpsd or the PPS setup. All of it is inside the optional SDR stack (`GTP_SDR=1`).

## The cause (observed)

On the owner's Pi on rc.8, `gps-time-readsb` logged:

```
readsb: ERROR: Unknown device type:rtlsdr
invoked by: /usr/bin/readsb --quiet --device-type rtlsdr --device 00000001 ...
```

Debian 13's `readsb` package is built without RTL-SDR support: its device types are only `ifile` and `none`. So readsb exited at once and restarted, and tar1090 (whose page now loads) had no data: `data/aircraft.json` was 404. rc.8 made the serial required; with it set, this is what was left.

## What's fixed and new

| What | Guide |
|---|---|
| **readsb built with RTL-SDR support:** wiedehopf's readsb v3.16.21 (commit `3219318`, 2026-11-01), cloned as `nobody`, the commit checked, `make RTLSDR=yes`, installed as `/usr/local/bin/readsb`. Every readsb unit uses it (the 1090 MHz decoder, the feeders and node mode). Debian's package isn't installed any more; one that's there is left alone and its `readsb.service` stays masked. | `deploy/sdr-stack.md` → "readsb with RTL-SDR support" |
| **The check:** `readsb --device-type rtlsdr --gtp-check-only`. The made-up option stops readsb at its argument parser either way, so the check never opens a dongle; without RTL-SDR support readsb says `Unknown device type` first. A failing build isn't installed or enabled: `CHECK FAILED`, exit 3, and `install.sh` says it again at the end. (`readsb --device-type rtlsdr --help` isn't used: readsb stops for `--help` only as the first argument, so it would start decoding.) | same |
| **dump978-fa checked the same way:** SoapySDR's RTL-SDR driver (`librtlsdrSupport.so`, `soapysdr-module-rtlsdr`) must be there for its `--sdr driver=rtlsdr,serial=…`. Without it, with a 978 MHz serial, dump978-fa isn't enabled and the installer says `CHECK FAILED`. | same |
| **The preflight** (`sdr-stack.sh check`) reports both: whether a readsb with RTL-SDR support is there yet and whether the driver is. It doesn't refuse, since the install adds both. | same |
| **The owner's serials:** `00001090` for 1090 MHz and `00000978` for 978 MHz. The warning for a serial rtl-sdr could read as a device index stays. | `deploy/sdr-stack.md` → "Two dongles" |
| **Aviation:** the stale "ADS-B / UAT — PLANNED, needs dump1090/dump978 integration" card is gone. In its place, the 978 MHz UAT map card: its state (live, paused, stale, no data, not installed), aircraft and data age, and a link to `/skyaware978/`. Both map cards come from one poll of `/api/aircraft-map`. | — |

**Why readsb and not dump1090-fa:** tar1090 is written for readsb's output (history files, `receiver.json`), and the units, the feeders' Beast output and node mode already use readsb's options. dump1090-fa isn't in Debian either, so it would also be a source build, and every one of those would change. Building readsb changes only the binary's path.

## What the upgrade changes on the station

With `GTP_SDR=1`:
- **Build packages:** `git`, `build-essential`, `pkg-config`, `libncurses-dev`, `zlib1g-dev`, `libzstd-dev`, `librtlsdr-dev`, `libusb-1.0-0-dev`. The build takes a few minutes on a Pi 4; later deploys with the same commit skip it.
- **New files:** `/usr/local/bin/readsb` and `/usr/local/lib/gps-time-sdr/readsb.commit`.
- **The units** `gps-time-readsb`, `gps-time-feed@`, `gps-time-readsb-node`, and the feeders' and node mode's readsb drop-ins, run `/usr/local/bin/readsb`.
- **Debian's `readsb` package stays installed if it is** (masked, unused). To remove it: `sudo apt-get remove readsb`.

## Deploy

From a clean working tree on Windows, in a normal PowerShell window. These are the flags for the owner's Pi after renaming the 1090 MHz dongle: SN `00001090` for 1090 MHz and the web SDR, SN `00000978` for 978 MHz. **Rename first** (`deploy/sdr-stack.md` → "Two dongles": stop the decoders and the web SDR, plug in the 1090 MHz dongle alone, `rtl_eeprom -s 00001090`, replug), or the 1090 MHz serial won't be found.

```powershell
git fetch --tags
git checkout v1.6.0-rc.9
git describe --tags --dirty          # must print exactly v1.6.0-rc.9

$env:GTP_SDR = '1'
$env:GTP_SDR_1090_SERIAL = '00001090'    # required; 'none' for no 1090 MHz role
$env:GTP_SDR_978_SERIAL = '00000978'     # 'none' with one dongle
$env:GTP_SDR_PPS_SERIAL = ''             # no PPS-marker dongle
$env:GTP_TAR1090 = '1'                   # the 1090 MHz map
$env:GTP_WEBSDR = '1'                    # re-run so its dongle drop-in follows the new serial
$env:GTP_WEBSDR_SERIAL = '00001090'      # the 1090 MHz dongle: readsb pauses while it runs
$env:GTP_WEBSDR_PORT = '8073'
$env:GTP_WEBSDR_MAX_HOURS = '4'
$env:GTP_WEBSDR_AUTH = '0'
$env:GTP_WEBSDR_REMEMBER_DAYS = '30'
$env:GTP_WEBSDR_HF = 'off'
$env:GTP_FEEDERS = '1'                   # each feeder stays off until turned on in Administration
$env:GTP_FEEDERS_PIAWARE = '0'
$env:GTP_FEEDERS_CUSTOM = ''
$env:GTP_INDEPENDENT_REFS = ''
$env:GTP_KEEP_DHCP_NTP = ''
$env:GTP_CLIPS_DIR = ''
$env:GTP_CLIPS_MAX_MB = ''
$env:GTP_SDR_NODE = ''
$env:GTP_NODE = ''
$env:GTP_NODE_STATION = ''
powershell -ExecutionPolicy Bypass -File .\scripts\deploy-to-pi.ps1 -PiHost $PiHost -PiUser $PiUser
git checkout main
```

`GTP_WEBSDR_SERIAL` must change with the rename: rc.8 saved `00000001`. Then read the deploy output:
- `== SDR stack: readsb v3.16.21 with RTL-SDR support ==` should end with `built with RTL-SDR support and installed as /usr/local/bin/readsb`.
- `== SDR stack: SoapySDR's RTL-SDR driver (dump978-fa) ==` should say it's installed.
- `== SDR stack: check after 10 s ==`: each decoder `is active` and its `aircraft.json` `exists`.

Then open Aviation (both map cards), `http://<pi>/tar1090/` and `http://<pi>/skyaware978/`. Remove the flags afterwards (`Remove-Item env:GTP_*`). By hand on the Pi: `/usr/local/bin/readsb --device-type rtlsdr --gtp-check-only` should print `unrecognized option`, not `Unknown device type`.

## Not yet verified on a Pi

- The readsb build under Debian 13's compiler on the Pi (readsb builds with `-Werror`), and how long it takes.
- readsb from `/usr/local/bin` opening `00001090` by serial with both dongles plugged in, and tar1090's data then answering.
- The check's wording against the real binaries: the RTL-SDR build's error for the made-up option, and Debian's for `rtlsdr` (the latter matches the owner's log).
- The SoapySDR driver's file path on the Pi (`/usr/lib/aarch64-linux-gnu/SoapySDR/modules0.8*/librtlsdrSupport.so` is expected).
- Everything in [`v1.6.0-rc.8.md`](v1.6.0-rc.8.md) → "Not yet verified on a Pi" still applies.

## Rollback

Check out `v1.6.0-rc.8` and run the same deploy command. rc.8 installs Debian's readsb again and its units point at `/usr/bin/readsb`, which has no RTL-SDR support, so 1090 MHz stops again. `/usr/local/bin/readsb` stays and does no harm; to remove it: `sudo rm /usr/local/bin/readsb /usr/local/lib/gps-time-sdr/readsb.commit`.
